# How this kit was built

Built 2026-10-18. This page is for someone deciding whether to trust the kit, or to copy the way it was made. It is about method, not code.

## The short version

The pass bars were written before any code. Each step was built as the smallest runnable thing, checked by a script, and then widened. The kit counted as done only after two rounds in a row passed every script gate and a reader who had never seen it understood the README. The test data was produced by rules, so no model ever graded a model.

## Why the eval sheet came first

Before writing a line of code we wrote a table: for each artifact (code, README, comparison report, explainer page, demo recording, skill file, privacy check), what "good" means and what checks it. Writing it first does three things.

- It stops the bar from drifting toward whatever the build happened to produce. A bar written after the work is a description of the work.
- It makes "done" a lookup, not a feeling. Every line on the sheet is either green with pasted evidence or not done.
- It forces the hard question early: who or what can check this? Where the answer was "a script", we used a script. Where it had to be a person or a model, we named which one, and made sure it was never the one that built the thing.

What each bar protects:

| Bar | What it protects |
|---|---|
| Tests pass with no API key | A stranger can verify the kit offline, in under two minutes, with nothing to sign up for. |
| Live tests only when a key is set | The real behavior is tested, but nobody is forced to spend money to run the suite. |
| Demo mode is labeled as recorded | Nobody mistakes a replayed response for a live one. |
| README read cold by a fresh reader, twice | The page explains the kit to someone with zero context, not to its author. |
| Comparison report with n, dates, model ids and the reproduce command | A number that cannot be reproduced is a claim, not a result. |
| Explainer page under 150 KB, opens from a file | It works with no server, no build step and no network. |
| Skill file kept thin | An agent reading it spends its attention on the task, not on our notes. |
| Privacy scan plus a grep plus a semantic read | Scripts catch strings; a reader catches paraphrased private stories that no pattern would. |
| Fresh clone test | "Works on my machine" is not evidence. A clean directory and a stripped environment is. |

## The loop

1. Build the smallest runnable thing: one client, one subcommand, one test.
2. Run a checker after every step. The checker is a script where a script can measure the thing, and a small cheap model confirming that the file exists and matches its spec line where it cannot.
3. Find the mistakes by running every gate, correct them, and write one line in the changelog per round. Each round is a version.
4. Widen: more subcommands, fixtures, README, explainer page, demo recording, skill file, comparison report.
5. Stop rule: at least version 3, and two consecutive rounds where every script gate passes and the cold reader passes. One passing round can be luck. Two in a row, after a change in between, is much harder to fake.

The order matters. A checker added at the end finds problems that are expensive to fix. A checker added after every step finds them while the change is still small.

## Why the fixtures are generated by rules

The kit needs labeled examples to measure against. There are two ways to get them, and one is a trap.

- The trap: ask a model to write the examples and label them. Then any comparison against that model, or a close relative, measures agreement with the labeler. A model is grading itself.
- What we did: a short generator script writes the examples from templates, and each template carries its label by construction. A command built from a "delete everything" template is labeled destructive because of how it was made, not because anyone judged it. The generator ships with the kit, so anyone can regenerate the data and get the same labels.

The consequence is a known cost: rule-made examples are cleaner and more regular than real traffic. That is the next section.

## What a golden set is, and why these fixtures are not one

A golden set is a collection of real items, labeled by people who know the domain, ideally by more than one of them with disagreements resolved. It is the thing you would trust to say "this works on our traffic".

Our fixtures are not that. They are synthetic, labeled by construction, and regular by design. They are good for what they are good for: testing that the code behaves correctly, that the comparison harness works, and that results are reproducible by a stranger. They are not evidence about how the system performs on messy real input. One finding below shows the gap in practice. If you rely on a kit's output for real decisions, build a golden set from your own data and refit on it.

## How the skill is structured

Each kit ships a skill file for AI coding agents. The structure is deliberate.

- A thin index, under 60 lines, whose description names the phrases that should trigger it and stays quiet on near-miss phrases. The trigger test uses three intended phrases and two decoys.
- The detail lives in a references folder. The last line of the skill file is a pointer to it.
- Why thin: a skill file is loaded into an agent's working memory whenever it triggers. Everything in it competes with the user's actual task. The index says when to use the kit and where to look; the references hold the depth and are read only when needed.

## Where Jev sits

Jev is a small model that returns typed judgments: a probability for a yes or no question, a confidence for a choice, a score. It sorts items. It does not decide them.

- Jev produces numbers. Code applies thresholds to those numbers and splits items into three bands: act, review, escalate.
- The uncertain band goes to a person or a stronger, slower model.
- This division is why the kits are built around thresholds and bands. The model is cheap and fast enough to look at everything; the expensive judgment is reserved for the items where it is actually needed.

A design that lets the small model make the final call has no safety margin. A design that lets code read its confidence and route accordingly does.

## What was measured, and what was not

Measured:

- Agreement and accuracy of Jev against rule-generated labels, on a stratified sample of 40 fixture items per kit.
- Median latency and cost per 1,000 items, compared against a general model called through its command line.
- For the ranking kit, rank correlation and top-10 overlap against a gold ranking made by construction.
- The test suites, the privacy scans, the fresh-clone run, and the console of each explainer page.

Not measured:

- Performance on real, messy, human-written input at scale. Forty synthetic items per kit is a smoke test with a number attached, not a benchmark.
- Whether thresholds transfer between datasets. The one thing we saw points to no: thresholds fit on synthetic data did not carry over to real traffic. That is why the threshold lab refits per dataset, and why every policy file carries a note saying so.
- Long-run drift, multi-language text, or images (images are in a beta and out of scope).
- Anything about how the explanations behind a judgment look. Jev returns numbers, not reasons.

## What to copy

Even if you never use these kits: write the pass bars first, name who checks each one, make test data whose labels cannot come from the thing under test, and do not call it done on the first green run.

## jev-cascade: what this kit measured and did not

- Measured, live, 2026-10-18: Jev `jev-1.13.0` on 120 synthetic support tickets, four questions per call, 83,193 input tokens, 0.19 s median per call.
- Measured, live: `claude -p --model sonnet --setting-sources project` as stage two, 4.02 s median, on the tickets the default policy escalated.
- Measured, replayed: two policies (default, and sentiment lowered to act 0.60 by hand) over the same recordings, with no model call repeated: 68 versus 46 escalations, 425 versus 422 correct of 480 field answers.
- Measured: whether stage two beat stage one on the same escalated items, 137 against 131 of 160 field answers at the default policy.
- Not measured: stage two ran on only 40 of the 68 escalated tickets, so end-to-end accuracy is below a full run's and the second-stage margin has n=40 behind it.
- Not measured: real tickets. The 120 are synthetic, labeled by the generator's rules, so every number is a smoke test with a number attached.
- Not measured: stage-two cost. The claude CLI is a subscription here, so the report prints zero and says why.
- Not measured: the tuned policy against a fitted one. The 0.60 line was set by hand from the recorded run; jev-threshold-lab is the tool that fits it.
- Not measured: the explainer's latency figure is a weighted average of two medians, an estimate, not a timed run.
- The explainer page recomputes the report's numbers in the browser; at the default lines they match the printed report to the ticket.
